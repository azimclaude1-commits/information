# AI诊股独立项目：功能盘点与需求确认

日期：2026-10-13  
状态：需求确认稿。本文是原型盘点，不是最终开发计划；技术选型、供应商、排期和预算待确认后确定。

## 1. 本次分析范围与依据

根据当前项目的路由、组件、数据文件和服务端实现，分析「AI诊股」导航下实际可到达的功能。没有修改现有业务代码，也没有执行真实模型调用或验证第三方数据接口。

当前有效路由为：

| 子页面 | 路由 | 实际承载组件 |
| --- | --- | --- |
| AI诊股 | `#diagnose/diagnosis` | `ResearchView` → `AiDiagnoseView` |
| Ace智搜 | `#diagnose/ace` | `ResearchView` → `MarketOverviewView` 的 ace 分支 |
| 热门榜单 | `#diagnose/hotlist` | `ResearchView` → `MarketOverviewView` 的 hotlist 分支 |
| 云图 | `#diagnose/heatmap` | `ResearchView` → `MarketCloud` |

重要边界：`MarketOverviewView` 还保留了市场概览和另一套云图代码，但它们不是当前「AI诊股」一级标签下额外可到达的子页面。诊股组件内残留的快讯、社区指标状态也不等于实际开放功能；当前底部只渲染两个标签。

| A04 | 输入市场问题或标的代码 | 匹配标的和关键词，返回预先编写的回答 | 大模型问答、上下文、标的识别、行情工具和资料检索 |
| A05 | 继续追问 | 将问答追加到页面；并没有真正基于此前对话推理 | 多轮上下文、上下文截断、持久化、回答取消及错误重试 |
| A06 | K线分析入口 | 固定跳到 NVDA 诊股，没有独立 K 线分析流程 | 是否只复用诊股，或增加选标的、选周期和图表分析 |

当前没有流式生成、联网搜索、新闻/财报检索、资料引用、真实会话历史、文件上传和回测。后几项中，文件上传和回测属于需要确认的新需求，不能因为页面叫「智搜」就默认加入。

## 4. 热门榜单功能清单

实际有九个榜单，代码中「12 卡」等旧注释不能作为需求数量依据。

| 编号 | 榜单 | 当前内容 | 真实实现需要的口径或数据 |
| --- | --- | --- | --- |
| H01 | 比特币 ETF | 固定基金名称、价格、涨跌幅 | ETF 真实标的与报价；是否还需要申购赎回/资金流另行确认 |
| H02 | 热门搜索榜 | 固定排序和数值 | 自有产品的搜索行为，或明确标注的外部热度数据 |
| H03 | 涨幅榜（24H） | 固定排行 | 可比较的标的池、真实涨幅、交易时段和排序 |
| H04 | 跌幅榜（24H） | 固定排行 | 同上 |
| H05 | 成交额榜 | 固定价格和成交额 | 成交量与成交额区分、币种换算、平台范围、时间窗口 |
| H06 | 实时大额爆仓单 | 固定事件，混有币永续及 CFD | 可获得的爆仓事件；交易所事件与自有模拟账户事件分开 |
| H07 | 合约持仓量（OI） | 固定排行 | 合约、平台、张数/币数/名义金额及统计时点 |
| H08 | 资金费率异动 | 固定排行 | 真实费率、结算周期、交易所和比较口径 |
| H09 | 主力净流入榜 | 固定数值，混合股票、加密和商品 | 明确定义净流入，说明是否为统计估算；不能等同于识别机构身份 |

通用交互：总览或单榜筛选、表格显示、点击行打开诊股。目前路由外层将榜单的 onQuickTrade 实际接到诊股入口，因此榜单行不会直接跳到下单面板。

重要身份问题：比特币 ETF 各行当前都映射为 BTC/USD。真实版本必须区分基金本身与底层资产，否则详情、诊股和交易跳转都会错。

## 6. 现有 AI 与后端实现的实际状态

唯一业务接口为 `POST /api/diagnose`，由 Express 实现，使用 GoogleGenAI SDK。代码写入的模型标识为 `gemini-3.8-flash`；本次只确认代码内容，没有确认该模型标识是否实际可用。

接口由浏览器提交 symbol、name、price、changePercent、lang。服务端把这些值放入提示词，让模型返回综合评分、方向、目标价、止损价及几段说明。

现状需要重做的关键点：

1. 服务端没有接入 K 线、指标、财报、新闻、成交明细等证据，无法据此核验技术、基本面和资金流结论。
2. 缺少请求校验、访问鉴权、用户额度、模型调用超时、缓存、任务队列、成本记录及可观察的错误分类。
3. 无密钥、模型失败或空响应时，统一返回 HTTP 200 和 fallback；前端随后显示模板报告，用户不能区分真实 AI 与演示报告。
4. 前端在生产构建中直接使用模板，不调用上述接口。不能以生产页面出现文字作为真实 AI 功能已完成的验收依据。
5. 现有服务端返回结构没有五维分项评分与三类策略说明；前端把模型结果与模板混合，五维分数强制保留模板值。
6. 综合分、固定 RSI、固定概率、固定买盘比例、暗池及机构挂单描述均没有对应证据；它们只能视为原型展示。
7. 行情在 App 中每 1.4 秒做随机变动；当前也没有真实行情服务连接。交易图表的历史 K 线来自演示生成，不应作为新项目真实分析输入。
8. 当前没有数据库、真实会话历史或报告版本记录；模拟账户的本地存储不等于用户服务端账户体系。

## 7. 独立项目的职责划分方向（待确认）

后端：标的目录、数据连接与快照、技术指标和评分规则、报告任务、会话与消息、资料检索、榜单与云图聚合、鉴权/额度、日志与配置。

AI：识别提问意图和标的、调用受控的数据工具、基于证据组织解读、输出规定结构、给出引用、识别缺失数据；数值计算应有可复核的方法。是否生成指标代码属于单独范围。

独立前端：四个页面、真实接口联调、加载/生成/缺失/过期/失败等状态、来源与时间显示、会话交互、图表和云图、手机适配。是否演示模拟成交需确认。

给技术团队的交付：稳定 API 约定、标的映射、请求/响应及错误示例、流式事件说明、联调样例、鉴权及跳转约定、启动部署说明。团队接入后应无需承担模型提示词、数据聚合和 AI 任务编排。

模拟交易引擎、账户资金、主产品用户注册、资讯门户和直播功能的归属需要明确；不能因复用原型前端而默认由本独立项目全部承担。

## 8. 需要用户确认的问题

建议按编号回答；暂时不知道的项可写「请你建议」，但预算和团队接口资源会影响排期可信度。

1. **首期验收目标**：四页全部真实可用、先做诊股和智搜，还是先做明确标注模拟数据的完整演示？九个榜单是否必须全部保留？
2. **市场范围**：仅美股、美股与加密货币，还是加上外汇/商品/指数？若包含加密，是现货、永续，还是两者都做？是否还希望新增 A 股/港股？
3. **已有资源**：团队是否已有行情、历史 K 线、财报、新闻、资金流数据接口和可使用的大模型服务？有哪些官方文档或接口说明可以提供？不需要在对话中提供密钥。
4. **交付与预算**：首版期望日期、每月模型与数据预算、内部演示或面向真实用户、初期大致用户量/每日提问量。
5. **数据要求与删减权限**：是否接受明确标注的延迟行情？没有真实来源的暗池、机构挂单、多空情绪、全平台报价等，能否暂隐藏或替换为有证据的数据？还是必须采购后交付？
6. **诊股输出边界**：保留具体目标价、止损、仓位和做多/做空策略，还是首期以走势分析、参考价位和风险解释为主？五维评分是否必须保持原样，能否按资产类型替换不适用维度？
7. **智搜边界**：是否必须联网检索并附来源、多轮追问与历史保存？「K线分析」是否需要独立图表流程？「AI写指标」是生成可复制代码，还是必须能在站内运行/回测？
8. **团队对接与用户体系**：团队偏好的后端语言或框架、API 调用方式、已有登录体系；接口是否使用他们的用户身份？是否需要额度/付费控制？若暂无答案，可提供技术负责人给出的接口约束。
9. **部署与展示端**：运行在境内还是境外，是否已有服务器/域名/数据库？首期是否同时支持手机、桌面、中文英文和深浅主题？独立前端是否复用原型风格？
10. **模拟交易与长期维护**：独立前端只需跳到主产品模拟下单，还是自身也要演示虚拟下单、持仓和平仓？上线后由谁维护数据源、模型配置、费用和服务故障？是否需要简单管理后台？

## 9. 确认后最终开发计划应包含的内容

- 明确的首期/后续范围和逐功能验收标准。
- 数据资源表：来源、覆盖范围、刷新时间、限制、费用和缺失时行为。
- 前后端与 AI 的项目结构、核心数据模型及可部署架构。
- API 合同、异步/流式流程、鉴权、错误和技术团队联调约定。
- 诊股评分、技术计算、证据检索、提示词、结构校验和质量评估方案。
- 独立前端页面与完整用户流程，包括失败、缺失、过期和空状态。
- 可直接交给 AI 开发的分阶段任务：输入、依赖、输出、验收、验证方式和完成条件。
- 数据正确性、接口、端到端流程、AI 证据一致性、性能与成本检查。
- 本地启动、配置、部署、备份、监控、运维和交接说明。
- 基于确认范围与资源的时间估算、成本区间、关键依赖和需要人工负责的事项。
